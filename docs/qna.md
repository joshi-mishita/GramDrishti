# Likely jury questions

Short, honest answers. Every number here comes from `verification.json` for model `s5-lgbm-9b632a7b1b` (see [validation_report.md](validation_report.md)) or from the code. Read these aloud with your teammate before the demo; if an answer sounds bigger than what we built, cut it down.

## Data and honesty

**1. Is this real data?**
No. Everything is synthetic: a made-up district of 6 blocks, 90 Panchayats and 24 stations, generated by our own script. Every screen says "Synthetic demo data. Not real weather." We have no real data and no data-sharing agreement.

**2. Then what do your accuracy numbers prove?**
That the method and the code work on data built to resemble the problem, and that our evaluation is set up correctly. They do not prove the model works on real weather. That needs real stations ([mock_to_real_plan.md](mock_to_real_plan.md)).

**3. How do you know it beats the block forecast?**
On a held-out test period (July to December 2024, 73,800 forecasts per variable), opened once and logged, the Panchayat forecast has lower mean absolute error than the raw block forecast for all five variables, with 95 % bootstrap intervals above zero. Against the bias-corrected block forecast it is better for temperature, humidity and wind (1.9 % to 5.1 %) and ties on rain. Leave-one-block-out and a station check give the same verdicts.

**4. So most of the gain is bias correction?**
Yes, and we say so. For rain all of the gain over the raw block forecast comes from correcting the block forecast; for wind 97 % and for minimum temperature 77 %. The Panchayat detail adds a few percent for temperature, humidity and wind.

**5. Where does it not help?**
Rain amounts: no better than the corrected block forecast, and worse on light and moderate rain days and in poorly drained Panchayats. Heavy rain (35 mm or more): worse than climatology and far below the block forecast. The heat alert raises three times as many false alarms as the block rule (1,628 against 527). The verification screen lists every such case.

**6. How did you avoid fooling yourselves?**
Splits by time and by block, never random. Three separate windows: train, calibrate, test. The test window can only be opened by the verification job, which first writes a ledger entry; opening it again for a new model version is marked "test reused". The synthetic truth is never a model feature. The protocol was written before the test window was opened.

**7. Did you tune on the test set?**
No. It was opened once on 2026-09-27; a rerun reproduced every number exactly. The rain result is a tie and we left it as a tie.

## Method

**8. What is the method, in one breath?**
Correct the block forecast's bias, predict each Panchayat's departure from it with LightGBM using terrain, land cover, soil, satellite and recent rain, give a range with conformal calibration, then shift the Panchayat values so they average back exactly to the block forecast.

**9. Why must Panchayats average back to the block?**
So the Panchayat forecast never contradicts the official block forecast; it only distributes it. A test enforces the gap below 1e-6; on the test period the largest gap was 1.4e-14.

**10. How good is the uncertainty?**
Mixed. The 80 % range covers 78 % for maximum temperature (slightly too narrow), 81 % for minimum temperature, 85 % for humidity and 90 % for wind (too wide). For rain on wet days it covers only 51 %.

**11. What if stations are sparse?**
Then the model is trained only where stations exist and validated leave-one-station-out, with a simpler model and wide intervals. If that is too thin, the fallback in the Backend Guide is to train on a gridded reference such as IMERG or ERA5-Land and validate only on real stations, labelled as a proxy method everywhere. None of this is built yet.

**12. Why LightGBM and not deep learning?**
Tabular features, two years of data, and we need quantiles, speed and explanations (SHAP). We did not try a deep model; with this little data we would not expect it to do better, and it would be harder to explain.

## Advisories

**13. Who sets the thresholds?**
Today, we did, as placeholders. Every advisory carries `thresholds_status: placeholder` and the screen says "pending expert review". The full list is in `docs/thresholds_for_expert_review.md` for a KVK or agriculture-university expert ([expert_review_pack.md](expert_review_pack.md)). No expert has reviewed them yet.

**14. How do you avoid wrong advisories?**
Three layers: advice comes from readable YAML rules, not a language model; every card shows its reason, the numbers behind it and a fallback ("if things change"); and nothing reaches a farmer until an officer approves or edits it, with an audit log. The thresholds still need an expert, and the rules have not been tested against real outcomes.

**15. Do you use an LLM anywhere?**
No. Advice text comes from templates in `advisory/templates.yaml`, filled with numbers by the rules engine. A test (`backend/tests/test_advisory.py`) fails if any backend module imports a language-model library.

**16. Are the Hindi and Punjabi texts correct?**
They are our drafts and marked as needing native review. No native speaker has checked them yet; `docs/translation_notes.md` lists the words we were unsure of.

**17. Can the farmer trust the spray advice by the hour?**
No, and we do not offer it. The data is daily, so spray ratings are for whole days.

## Product

**18. What does the officer actually do?**
Opens the priority list of Panchayats that need attention, reviews drafted advisories (approve, edit or reject), and prints a village bulletin. On a heavy-rain day that is 198 drafts for 90 Panchayats; there is no bulk approve yet.

**19. How does it reach farmers without smartphones?**
Today: a printable one-page bulletin per Panchayat, and audio in the app. WhatsApp sharing opens a message with the text. IVR and SMS are not built.

**20. Does it work offline?**
The farmer app caches what it has shown and reloads offline; a rain report made offline is sent when the phone is back online. The whole demo also runs from exported files with no server (port 8081). Tested in desktop Chrome's offline mode, not on a real phone.

**21. What happens with farmer feedback?**
It is stored and can be checked against stations. It does not change forecasts or retrain anything; the app says the report "helps us check the forecast".

## Scale, cost, privacy

**22. How does it scale?**
The heavy work runs once per day offline; the API only reads precomputed files, which answered in a median of 3.2 to 6.2 ms per request on a laptop (70 ms for the priority list). One district is 90 Panchayats. For many districts we would move SQLite to PostgreSQL, add a scheduler and a model registry; that is a plan, not built ([architecture.md](architecture.md)).

**23. What are the privacy considerations?**
We store no phone numbers, addresses or ID numbers. A farmer profile holds Panchayat, language, crops and livestock; a rain report holds Panchayat, date and answer, not who sent it. Logs contain no personal data. There is no login yet, so a real deployment needs officer accounts before anything is sent.

**24. What would it cost to run?**
We have not costed it. The prototype runs on one laptop in Docker; the audio uses gTTS, which needs internet and would be replaced by an agreed speech service.

**25. Are you working with IMD, a state department or a KVK?**
No. We have no partnership or data agreement with anyone. The real sources in the data card are names of where data could come from, each marked to be verified.
